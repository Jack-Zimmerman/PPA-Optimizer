# Session 3 — pipelining, the report, documentation, speed analysis, native build, continuing runs

Date: 2026-10-27. Picks up from [session2.md](session2.md) (verification gate, dev agents, iteration loop, first real runs). Some of today's technical detail was written straight into session2.md sections 4b-4e; this file is the day's story and results, with pointers.

## Where we started
The fp16_multiply loop (3 rounds, cycle-exact only) had reached setup slack -0.756 ns at the 5.0 ns target, from -1.670 ns, with area 13277.7 um^2 (baseline 13033.8). Options were: more rounds, a relaxed clock (~5.8 ns), or allow extra latency.

## 1. Pipeline stages (`MAXLAT`)
Decisions: extra latency is allowed only by an explicit per-run flag, and pipelining is tried only after cycle-exact rewrites stall.
- `make iterate ... MAXLAT=N` (`--max-extra-latency`), default 0. `PIPENOW=1` (`--pipeline-now`) allows the full `MAXLAT` from round 1; without it a one-round run can never pipeline, because the allowance starts at 0 and rises one stage per stalled round.
- Gate (`ppa_opt/verify/latency.py`, `gate.py`, `cocotb_test.py`, `bench.py`): the cycle-exact check always runs first. On a mismatch, a second run compares DUT output at cycle t with the model output at cycle t-k for every k up to `MAXLAT`, and reports the smallest k with no mismatch (`GateResult.latency_extra`). Outputs are not checked for k+1 cycles after a reset, and the suite's SVA is skipped in that run (it assumes the original latency), so it is a weaker check. A design wrong at every delay reports the first mismatch per delay tried.
- Loop: among designs that meet timing, less added latency wins, then smaller area; once timing is met the latency is frozen. The final report and `best.json` warn that added latency means the design is not a drop-in replacement. `rtl-author` has a "PIPELINE MODE" section (exactly L balanced stages, output registers keep the spec's reset behaviour).
- Tests: hand-written 1-stage ALU (`tests/data/alu_p_pipe1*.sv`) is rejected strictly and accepted as +1 with an allowance; a buggy copy is still rejected; cycle-exact designs stay at 0; loop escalation tested with fakes.

## 2. Real pipelining runs on fp16_multiply (5.0 ns)

| `fp16_multiply_r4` | 1 round, 4 rewrites + 2 knobs, `MAXLAT=1`, `PIPENOW=1`, from the -0.756 ns design | `r1c0` | **+0.039 ns (met)** | 13371.6 um^2 | +1 cycle |

- With one extra stage timing is met at 5.0 ns with only about 2.6% more area than the original baseline (13033.8) and 0.7% more than the best cycle-exact design (13277.7). In that run two rewrites were pipelined (`r1c0`, `r1c1`, identical results) and two stayed cycle-exact (-2.229 and -1.832 ns). The flow knobs again changed nothing useful (-0.763/-0.756 ns).
- In the 8-rewrite run four pipelined rewrites met timing (+0.905 to +1.142 ns) at 20.2k-21.5k um^2 (+10 cycles); the cycle-exact `r1c4` still violated (-1.705 ns); three rewrites (`r1c5`-`r1c7`) were rejected for adding ports.
- The +1 result is the practical one. Whether +1 latency is acceptable is a decision about the spec, not the tool.

## 4. Documentation requirement for candidates
`rtl-author` must start every file with a header (Strategy, What changed, Why it helps, Equivalence, Latency, Tradeoffs), comment every always/assign/generate/function/case block, and mark changed logic with `// OPT:`. The rewrite prompt repeats it. `iterate.comment_check()` flags missing headers or uncommented blocks (printed, saved as `doc_notes`, never rejects).
- Investigated why every candidate was flagged: the agents had followed the header rule; my checker only accepted a comment on the line directly above a block and so flagged blocks documented by a section comment above their declarations. Fixed (declarations and sibling `assign` lines no longer break the link). After the fix 4 of 8 files in the latest run were clean and 4 had real gaps (mostly pipeline-register `always_ff` blocks without their own comment); the agent instructions now say those blocks need their own line.

## 5. Why `make iterate` is slow, and options
Measured from the saved fp16_multiply run: a round took about 6.5-7.5 min; the six parallel flows took a median of 340 s, about 80-85% of a round. Inside one 346 s flow: detailed route 139 s (40%) and global route 109 s (32%), both single-threaded and CPU-bound; everything before routing about 45 s; everything after about 35 s. So more cores per flow do not help.
Options discussed: use idle CPUs (6 flows on 8 CPUs; the flow knobs added nothing, so use `N=6 KNOBS=0`); rank candidates after clock-tree synthesis and route only finalists (on the 19 saved fp16 runs the post-CTS slack matched the final slack with rank correlation 0.98 and a worst difference of 0.107 ns and picked the same winner, but on the alu_p runs, where timing was already met, it was poor, so it suits the timing-fix phase only; not built); run OpenROAD natively on arm64 (section 6); overlap agent and flow work (small gain). A GPU does not help: routing has no GPU version in OpenROAD, placement is about 10 s of 346, and Docker/Colima cannot reach the Apple GPU.

## 6. Native arm64 OpenROAD image (built and validated)
The Colima VM is aarch64, so a linux/arm64 image runs natively with no x86 emulation. A build agent was launched (it was cut off once by a session restart and then resumed). `docker/arm64/` holds the `Dockerfile` (pinned to the same ORFS / OpenROAD / Yosys / kepler-formal commits as today's x86 image, Ubuntu 22.04, `build_openroad.sh --local`, 5 threads), `build.sh`, `build.log`, and `build.attempt1.log`.
- Attempt 1 compiled KLayout (about an hour, while competing with flow runs) and then failed on `curl: Could not resolve host: download.docker.com`, a transient DNS error; a failed step is not cached, so attempt 2 redoes the whole dependency step.
- It took 9 attempts and several hours. Failures: the transient DNS error; OpenROAD's default Bazel build failing on arm64 (it compiles Qt 6.9.1 from source and breaks in `qsimd.cpp`, and the pinned slang tarball checksum no longer matches GitHub); the CMake tree's `TestResizer` unit-test target not compiling at this revision (worked around by building and installing only the `openroad` target); `-no-tests` breaking CMake configuration. OpenROAD is therefore built with CMake (gcc 11), which upstream says it removes on 2026-11-01. A prebuilt-binary route was checked: the GitHub `.deb` releases are amd64-only and from Dec 2024; newer ones are on VaultLink, whose arm64 availability could not be confirmed.
- Result: `ppa-orfs:arm64` (6.22 GB) with the pinned revisions (ORFS 0b56643, OpenROAD bc739ca, yosys a5af9d6, kepler-formal f70c2e3), KLayout 0.30.12 built from source, `read_slang` built into yosys. Files: `docker/arm64/{Dockerfile,build.sh,README.md,build.full.log}`.
- Validation (agent, 1 CPU each, partly under contention): area and cell counts identical to the x86 image for alu_p (2168.33 um^2, 886 cells) and fp16_multiply baseline (13033.8 um^2, 4681 cells); setup slack within 0.2 ps (alu_p) and 8.6 ps (fp16); power within 0.4%. Wall time: alu_p 181 s -> 106 s, fp16 baseline 346 s -> 275 s. Six parallel alu_p flows took 148 s wall (identical results), against 106 s for one.
- My own check on the fourth-round design (`fp16_multiply_r4` best, +1 cycle), both images run side by side on 1 CPU each with identical inputs: arm64 250 s vs x86 345 s; area 13371.6 and 1747 cells identical, setup slack +0.0399 vs +0.0387 ns, hold 0.3268 vs 0.3267 ns, power 7.3192 vs 7.3183 mW. By stage, detailed route barely changed (148 s vs 160 s) and global route 75 s vs 90 s; the gains are in synthesis, clock tree and layout merge. So the speedup is about 1.3-1.4x, not the 2x a simple CPU benchmark suggested (x86 emulation measured about 1.9x slower on a compiled checksum task); routing is memory-bound and loses little to emulation.
- Not yet done: the flow code still points at the x86 image. Switching means the image name and `--platform linux/arm64` in `ppa_opt/synth/openroad_flow.py`; the image id is in the cache key, so old cached results will not be reused. Run directories must live under `$HOME` (a path outside it is mounted but empty in the VM).

## 7. Runs now continue from their folder; an overwrite incident
The 8-rewrite run above was started with no `NAME=`, so it wrote into the same folder as the first fp16_multiply run (`work/iterations/fp16_multiply/`) and replaced its `history.json`, `best.sv`, `best.json` and `iter_0`/`iter_1`. That is why `make viz` showed only two rounds for it. The original three rounds (-1.670 -> -0.756 ns) are no longer in any history file; the later candidate files `iter_2`/`iter_3` and the flow results in `work/cache` and `work/runs` survive. The best cycle-exact design (`r3c1`) is still at `work/iterations/fp16_multiply/iter_3/cand1.sv`.
Fix: the run folder is now the memory of the run. If it has a history, `make iterate` starts from that run's `best.sv` (gated with its own latency), numbers new rounds after the last saved one, and appends to the same `history.json`; `RTL=` is only needed for a new run. It refuses to continue at a different `CLOCK` than the run's `best.json` records. `FRESH=1` (with an `RTL=`) moves the old folder to `<name>.old-<timestamp>` instead of deleting it. Five tests cover this. Note: the `fp16_multiply` folder's saved best is now the +10-cycle design, so continuing there builds on that; use `FRESH=1 RTL=.../iter_3/cand1.sv NAME=...` to keep working from the cycle-exact design.

## 8b. Later the same day: port-reader bug, pipelining rule, author failures
- **Port-reader bug (fixed).** `extract_ports` walked into function bodies and reported function arguments and return values (`csa`, `ks_add`, `lz11`, `norm11`, `m`, ...) as unexpected module ports, so valid designs that declared a function were rejected at the interface check: 5 of 12 round-1 candidates in one run, and `r1c5`-`r1c7` of the earlier 8-rewrite run. It now reads only the module's own port declarations. The five rejected candidates passed the suite when re-run, and a regression test covers functions and tasks.
- **Why `MAXLAT=4` did not pipeline.** The allowance rose only after a round with no timing improvement; in the run examined, every round improved (-1.415, -1.132, -0.609 ns) so it never rose and all measured designs had latency 0. New rule (chosen): also escalate when a round improves slack but closes under 25% of the remaining violation (`SLOW_GAIN_FRACTION`).
- **Author failures.** In the same run, rounds 4 and 5 recorded every rewrite as "author failed (exit 1)" with an empty message (round 4 still left 9 complete files on disk; round 5 left none); the stop message then wrongly said all rewrites were rejected. The cause is not confirmed (a usage or rate limit fits). Now: a file the agent wrote is still judged by the suite; a round with no file from any call stops the run cleanly (not recorded as a round, not counted as rejections) and can be continued; the agent's error text is kept; stale candidate files are deleted before each agent call.

## 8c. A run that looked stuck on round 1: the Mac went to sleep
A fresh `fp16_multiply` run sat on round 1 for about 25 minutes. The four flows started together at 00:35:51; their own stage logs summed to about 6 minutes each, but they finished 11, 13 and 24 minutes later. `pmset -g log` showed the Mac idle-sleeping at 00:47:35 (on battery) with a brief maintenance wake at 00:49:16 and waking at 00:58:38, so the Colima VM and every flow in it were suspended for about 11 minutes. Fix: `make iterate` and `make compare` now run under `caffeinate -i` (macOS only, skipped if absent). It does not prevent sleep on lid close. No data was lost.
